# Handoff: where the LabShope LIMS native app stands (30 Oct 2026)

Read this first if you are a new person or a new AI assistant account picking up this repository. It says what exists, how it is
built and released, what is live, what is waiting on a person, and the rules the owner asked us to follow. Older notes:
`PROGRESS_NOTES_2026-10-29.md`, `NATIVE_CLIENT_PLAN.md`, `NATIVE_FEATURE_PARITY.md`.

## What the product is
- **Web app** (this repo's `src/`, Vite + React, deployed by Cloudflare Pages from the `release` branch): the online LIMS for labs.
- **Native desktop app** (`native/`): an offline-first Windows / macOS / Ubuntu app that must reach feature parity with the web app, reusing
  its tables, rules and server functions (do not invent new server behaviour unless a migration is truly needed).
  .NET 6 + Avalonia 11 (so it runs on Windows 7 to 11), local SQLite per lab, outbox + sync engine, Velopack installers and auto-update.
- **Backend**: Supabase project `ceyfwoczyhnwipacwhcn` (Postgres + RLS + edge functions in `supabase/`).

## Working agreements (the owner's rules)
1. **Never push to `main`, `demo` or `production` directly.** Feature branch, pull request, CI green, the owner merges. Do not merge PRs yourself.
2. **No `Co-Authored-By: Claude` lines** (or other AI attribution) in commits or PR descriptions.
3. **Never run `supabase db push` or other production-changing commands yourself**; the owner applies migrations. Say which migration needs applying.
4. Do not paste tokens or keys anywhere. Secrets live in GitHub Actions secrets and Supabase secrets only.
5. Every change comes with tests (core tests, UI tests, and a real-database step in `IntegrationLocalTests` where the server is involved).
6. Keep messages to the owner short and plain; they run labs, not code.

## Environment gotchas
- Run dotnet / node tools with `env -u ELECTRON_RUN_AS_NODE` (the editor sets that variable and breaks them).
- On macOS use `sed -i ''`; zsh does not expand `--include=*.cs` unquoted.
- `.claude/settings.json` is no longer tracked (it used to show as modified).
- Native tests: `cd native && dotnet test tests/LabShope.Core.Tests -c Release` and `tests/LabShope.App.Tests` (headless Avalonia).
  Set `LABSHOPE_SHOT_DIR` to also save screenshots. The real-database test (`IntegrationLocalTests`) only runs when `LIMS_IT_*` variables point
  at a local Supabase; CI's Database job does that.
- The web app: `npm run typecheck`, `npm run lint`, `npx vitest run`.

## Branching, CI and releases
- `ci.yml` runs on every push and PR (web, desktop, native tests on Linux, database migrations + SQL tests + integration). On `main` it moves the `release`
  branch to the tested commit; **Cloudflare Pages deploys the web app from `release`**.
- **Installers are built only when a GitHub release is published** (`.github/workflows/native-release.yml`). The version is the tag without the `v`.
  **Right now only Windows (64 and 32-bit) is built**, to save GitHub Actions minutes (macOS minutes cost 10x, Windows 2x). The Mac and Linux lines are
  commented out in the matrix; remove the `# ` to bring them back.
- The release job uploads to the Cloudflare R2 bucket `labshope-lims` (see `docs/NATIVE_DOWNLOADS.md`):
  `releases/<version>/` (everything), `latest/LabShope-LIMS-<platform>.<ext>` (fixed names), `latest/latest.json` (what the website reads),
  and `updates/` (the Velopack update feed the installed apps check). Public address: `https://lims-downloads.labshope.com`.
  A Cloudflare Worker route sends every `*.labshope.com` host to the Pages app; `lims-downloads.labshope.com` has its own route with Worker "None".
- Download page on the website: `/download` (`src/components/platform/PlatformDownloadPage.tsx`); platforms missing from `latest.json` show "Coming soon".
- Auto-update: `native/src/LabShope.App/AppUpdater.cs`. Installed copies check 30 s after start and every 6 h, download quietly, and only restart when the
  user clicks "Update ready: restart". Copies from 1.0.x have no updater and need one manual install.
- Releases so far: v1.0.0 (Windows tests failed on a real bug; superseded), v1.0.1, v1.1.0 (adds auto-update). Next planned: 1.1.1 with patient email.

## What the native app can do now
Register visits (existing or new patient, tests, packages, referral, discount, payment, receipts/labels/reports), patients (search, edit, add alone,
switch off/on, history, email), results and worklist, analyzers (ASTM/HL7 over network or serial) and barcode scanning, bookings, bills (details, edit,
filters), payments, finance books, inventory (stock in/out plus add/edit/switch off items), catalog management (tests, packages, doctors, external labs,
categories, report templates), labs and collection centres, staff (add, edit, switch on/off, reset password), lab profile (name, contact, report footer,
logo), settings (printer, sync queue), forgot password, full screen, automatic updates. See `NATIVE_FEATURE_PARITY.md` for the full matrix.

## Security status (read before making the repository public)
A history scan on 30 Oct found real secrets committed over time. The cleanup PR deletes the files and `src/lib/__tests__/noSecrets.test.ts` now fails the build
if one comes back, **but the values stay in git history, so each one must be rotated** (changed at its provider) by the owner:
- **Mailjet API key and secret key** (in `deploy-edge-function.sh`, `set-email-secrets.sh` and several docs). After rotating, update the Supabase edge
  function secrets `MAILJET_API_KEY` / `MAILJET_SECRET_KEY`.
- **Razorpay key secret** (`RAZORPAY_KEY_SECRET` in an old setup guide). The key IDs (`rzp_...`) are public by design. After rotating, update the Razorpay settings
  / Supabase secrets used by `create-razorpay-order`.
- **A Supabase secret key (`sb_secret_...`)** in an old setup guide. Rotate it in the Supabase dashboard (Settings, API keys) and update anything that uses it.
- **SMTP credentials** (user and two different passwords) that were in a committed `.env` (`VITE_SMTP_*`). Change the mailbox password.
Publishable / anon keys, Turnstile site key and the Supabase project reference are meant to be public and do not need rotating.
Rewriting history (`git filter-repo`) is optional once everything above is rotated; it would change every commit id and close open PRs, so only do it deliberately.
